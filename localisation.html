Vehicle Mechatronics · Localisation

Where am I, exactly?

An automated vehicle fuses many answers to that question: satellites overhead, an inertial sensor that feels every motion, the wheels, and the shape of the world around it. Play with each one — then watch a real ICP solver localise a LiDAR scan against a map.

Inertial Measurement Unit

Feeling every motion — 6 degrees of freedom

An IMU measures acceleration along 3 axes and angular velocity about 3 axes. From a flat rest it feels only gravity pointing "up" through its z-axis; tilt it and gravity spreads into x and y. Tumble the chip and watch all six numbers, then see why the errors drift.

Wheel odometry

Counting the wheels

The simplest dead-reckoning sensor: an encoder counts each wheel’s rotation and turns it into distance. Cheap and always available, it is the backbone of vehicle odometry — but it drifts and lies the instant a wheel slips.

Wheel odometry — the other dead-reckoning sensor

An encoder counts wheel rotations; each tick is a known slice of a turn. Distance travelled = r·θ (radius × total angle), and speed v = r·ω. Roll the wheel and watch the odometer add up.

LiDAR odometry · point-cloud registration

The registration family

A LiDAR scan is a point cloud. Matching one scan to the next — or to a map — recovers the pose (X, Y, θ) that best overlaps them: that is LiDAR odometry. The four solvers below are all live; they differ in what they match. Correspondence-based ICP variants pair each scan point to a map point every iteration; correspondence-free NDT matches against a grid of Gaussians; distribution-to-distribution GICP weights the error by each surface's local shape. Start with the step-by-step ICP solver, then point-to-plane, NDT and GICP — and compare their live performance at the end.

How each iteration works

"Limited math" version — the same steps the slides derive with SVD (Kabsch algorithm).
Match: for every scan point, find the closest map point. (Correspondences are unknown, so we guess them each round.)
Centre: subtract each cloud's centroid, so only rotation remains: s̃ = s − s̄, m̃ = m − m̄.
Solve rotation R and translation t that minimise Σ‖m − R·s − t‖² (closed-form via SVD of the cross-covariance).
Apply & repeat: move the scan by (R, t). Re-match and iterate until it stops improving.

NDT · Normal Distributions Transform — live

correspondence-free

Divide the map into a grid of cells; describe each cell's points by a Gaussian (mean + covariance). Then slide the scan to maximise its likelihood under those Gaussians — no point pairing at all. Change the cell size and watch the cost surface coarsen or sharpen.

GICP · Generalised ICP — live

distribution-to-distribution

Give every point a local covariance — a little disc that's flat along the surface. Match disc-to-disc (plane-to-plane), weighting each error by both clouds' shape. Raise the anisotropy to make the discs flatter and the behaviour more plane-to-plane.

Sensor fusion · Kalman filter

Better than any one sensor

Here's the payoff, and where the registration you just built comes back. A Kalman filter fuses several flawed sources — each strong where another is weak. Build your own sensor suite below: switch wheel odometry, IMU, GNSS, LiDAR odometry and map registration on and off, and watch the fused estimate tighten or drift. Motion sensors predict; absolute sensors correct. Drive into the tunnel with only wheel odometry and the fix wanders; add registration and it locks back on — that's why AVs carry all of them.

Simultaneous Localisation & Mapping

Closing the loop — a globally consistent map

Every odometry source — wheel, IMU, LiDAR or visual — drifts, so a raw trajectory never quite closes. Full SLAM adds a back-end: keep a graph of poses, recognise revisited places (loop closure), and optimise the whole graph so the map stays globally consistent.

Loop closure & graph SLAM — RTAB-Map style

appearance-based

Odometry always drifts, so the estimated trajectory slowly bends away from the true path. The cure: recognise a place you've already seen and pin the two together. RTAB-Map spots it with an appearance-based bag-of-words image database, adds a loop-closure constraint, then a pose-graph optimiser redistributes the error and closes the loop. Drive it, close the loop, then optimise.

Odometry drift15
Press Drive the loop — watch the orange odometry trajectory bend away from the true green loop.
Front-end (odometry): track features frame-to-frame for a pose estimate. Accurate locally, but error accumulates — the loop doesn't close.
Keyframes + pose graph: store selected frames as graph nodes; consecutive nodes are linked by odometry edges (constraints).
Loop closure (appearance): RTAB-Map compares the current image to a bag-of-words database of past keyframes. A strong match → a new edge saying "these are the same place".
Back-end optimisation: a graph optimiser (g2o / GTSAM) spreads the loop-closure correction across every node — drift vanishes and the map stays consistent.
true loop odometry (drift) pose graph keyframe loop-closure edge
RTAB-Map's memory management keeps only the most relevant keyframes in "working memory" so loop-closure search stays real-time even on very large maps — the rest moves to long-term memory and is recalled when nearby.

And beyond registration

Once frame-to-frame alignment works, full SLAM systems add:

Particle filtersProbabilistic pose estimation over many hypotheses — e.g. FastSLAM / AMCL.
Graph SLAMOptimise a graph of poses; loop closure corrects accumulated drift — e.g. Cartographer.
Learned SLAMDeep networks estimate odometry directly from scans — e.g. LO-Net.
Why LiDARDirect, accurate range → generally more robust than camera-only SLAM.
Which to useIndoors / planar → point-to-plane or NDT; noisy or varied → GICP; huge maps → NDT.
Visual SLAM

Localising from a plain camera

Cameras are cheap and don't need depth — a stream of 2D images is enough. VSLAM detects features in each frame, matches them to the next frame, and recovers how the camera moved. The catch: a single camera can't recover scale — how far, only which direction — so IMU or stereo is fused back in.

Step 1 — Feature detection

A detector slides a small kernel over the image and fires where the texture is distinctive — corners, blobs. This is the intuition behind SIFT / SURF / ORB (and learned CNN detectors).

Step 2 — Match & estimate motion

The same features are found in the next frame; matching them reveals the camera's rotation and translation (up to scale) — the 8-point algorithm.
