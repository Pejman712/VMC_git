The middleware that robotics runs on.

Hardware

If it senses, there's probably a driver

A ROS driver (or “wrapper”) turns a sensor's proprietary output into a standard message any node can read. Because the message types are shared, swapping one LiDAR for another rarely changes the code downstream. Below is a representative sample of actively-maintained ROS 2 drivers — the full index lists thousands more.

Why this matters for your code: a Velodyne, an Ouster and a Hokuyo all publish sensor_msgs/LaserScan or PointCloud2. Your navigation node subscribes to the message, not the hardware — so the same node runs on any of them. That interchangeability is the whole point of the ecosystem.
Interactive · the core idea

Publish & subscribe, live

This is ROS in one picture. The talker node publishes messages to a topic (/chatter). Any listener that has subscribed receives every message. Press publish, change the rate, add listeners — then watch the same activity feed the tools below.

2 Hz
messages published: 0
// listener callbacks appear here — press “Publish”…

Topics are one-to-many: one publisher can feed many subscribers, and the talker neither knows nor cares how many are listening.

Beyond topics

Three more ways nodes talk

Topics are a fire-and-forget stream. But sometimes a node needs an answer, a long job with progress, or a shared setting. ROS builds three more patterns on top of topics — try each one.

Service

Ask & wait

A request → response call. The client waits, so services are for short jobs — “add these two numbers”, “test the headlights”.

add_two_ints +
// press “Call” to send a request…
Action

Long job, with feedback

For tasks that take time — “follow the path to the goal”. The client gets continuous feedback and can cancel. Result comes at the end.

// send a goal to start…
Parameter

Shared settings

Named values a node reads at runtime — like tuning gains. Set a PID gain here; the controller node picks it up when it reads the parameter.

controller.Kp 1.20
// set a value, then let the node read it…

Rule of thumb — continuous data? topic. Quick answer? service. Long task you monitor? action. A setting? parameter.

Command line

Talk to a running system

You rarely need a GUI to inspect ROS — the ros2 CLI shows you every node, topic and message live. Click a command to run it against a simulated robot.

robotics@VMC: ~/ros2_ws

These are the commands you'll reach for constantly — list to discover, echo to see data, hz to check rates, interface show to learn a message's fields.

Coordinate frames · tf2

Where is everything, relative to everything?

A robot is a stack of coordinate frames — the map, the robot base, each sensor. tf2 tracks the transform (translation + rotation) between them so any node can convert a point from one frame to another. Drag the sliders to move the camera on the robot and watch its transform update.

The transform tree

The whole robot as a chain of frames. Solid = static (bolted on). Dashed = dynamic (changes as the robot moves).

Developer tools

The three tools you'll live in

ROS gives you X-ray vision into a running system. These three are wired to the demo above — interact with it, then watch them respond.

rqt_graph — see the wiring

$ ros2 run rqt_graph rqt_graph

Nodes are ellipses, topics are boxes, and arrows show the direction data flows. This graph mirrors the live demo — add a listener above and it redraws.

RViz — see the world

$ rviz2

The 3D lens on your robot: sensor data, coordinate frames, maps and paths. Toggle displays to add or remove layers — exactly like the real panel.

X (roll) Y (pitch) Z (yaw) ● simulated /scan points

ros2 bag — record & replay

$ ros2 bag record -a

A bag records messages with their timestamps, so you can replay a run later — the system can't tell live data from a replay. Hit ● Record bag in the demo while publishing, then play it back here.
